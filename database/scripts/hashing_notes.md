# Cryptographic Hashing: Passwords vs. API Keys

This document explains the security, architectural, and performance rationale behind choosing different hashing strategies for user passwords versus API keys and webhooks.

## 1. Password Hashing (Argon2id, Bcrypt)
Password hashing is designed with the assumption that users choose relatively weak, guessable passwords, and that attacker compromises of databases are a realistic threat.

- **Slow by Design (CPU & Memory Hardness)**: Algorithms like Argon2id and Bcrypt intentionally consume significant CPU cycles and memory. Tuning them to take 250ms–500ms ensures that brute-force attempts or offline dictionary attacks are extremely expensive for an attacker.
- **Unique Salt (Salting)**: Each password hash includes a cryptographically secure random salt. This prevents **rainbow table attacks** (precomputed lists of hashes) and ensures that two users with the identical password will have completely different hashes stored in the database.
- **Why we use it**: To protect weak human-created secrets against offline dictionary/brute-force attacks if the database is leaked.

---

## 2. API Key & Token Hashing (SHA-256)
API keys and authentication tokens are generated by the system using cryptographically secure random number generators (e.g. `random_bytes()`), making them long and high-entropy.

- **Fast & Unsalted (SHA-256)**: SHA-256 is a fast cryptographic hashing function. Because the keys are randomly generated with 256 bits of entropy (e.g., 40+ random characters), they are mathematically impossible to brute-force or dictionary-attack, even without a salt or artificial slow-down.
- **Timing Attack Resistance (`hash_equals`)**: Because SHA-256 verification is extremely fast, it is susceptible to **timing attacks** (where an attacker guesses characters of the key and measures response times to determine how many characters match). To prevent this, comparisons must always be done in constant-time using `hash_equals()`.
- **Never use `Hash::make()` for API Keys**: Password hashing functions (like Bcrypt/Argon2id) are far too slow for API endpoints that handle high volumes of automated requests. Using them for API key validation would quickly result in a Denial of Service (DoS) under moderate load.
- **One-way Storage**: Plaintext API keys must only be shown once to the user upon creation. Only the fast SHA-256 hash `hash('sha256', $key)` is stored in the database for secure lookup.

---

## 3. Webhook Signature Verification (HMAC-SHA256)
Webhooks transport payloads over the public internet, requiring validation that the payload is authentic and was not altered in transit.

- **Keyed Hash (HMAC)**: Hashed Message Authentication Codes (HMAC) combine the raw payload body with a shared signing secret key.
- **Verification**: `hash_hmac('sha256', $payload, $secret)` computes a digest of the payload using the shared secret. If the calculated hash matches the signature header sent by the client, it proves both authenticity (originating from the secret holder) and integrity (not modified).
- **Constant-time Comparison**: Just like API keys, comparison of the computed HMAC signature against the incoming header must use `hash_equals()` to prevent timing attacks.
