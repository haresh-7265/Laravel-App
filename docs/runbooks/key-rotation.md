# Production Runbook: APP_KEY Rotation

This runbook outlines the technical details, security dependencies, and the step-by-step procedure to rotate the application key (`APP_KEY`) safely in production using Laravel's dual-key support.

---

## 1. What is the APP_KEY?

The `APP_KEY` is a 32-byte cryptographically secure random secret (encoded as base64 and prefixed with `base64:`) used by Laravel's encryption services. By default, it is used for:
- **Symmetric Encryption**: Used by the `Crypt` facade and Eloquent's `encrypted` casts (AES-256-CBC or AES-128-CBC).
- **Session Security**: Used to encrypt and sign session cookies, preventing users from tampering with session data.
- **Signed Routes & URLs**: Used to generate and verify HMAC-SHA256 signatures for URLs (e.g., email verification links, password resets, cancel email change URLs).

---

## 2. Key Dependencies & Impact Analysis

If the `APP_KEY` is rotated abruptly without setting up dual-key support, the following issues will occur immediately:

| Dependency | Mechanism | Impact of Abrupt Key Change |
| :--- | :--- | :--- |
| **Crypt & Encrypted Columns** | AES-256-CBC encryption | Reading any encrypted database column throws `Illuminate\Contracts\Encryption\DecryptException` (fatal application error). |
| **Session Cookies** | Signed/encrypted cookie payload | All user sessions are instantly invalidated. All logged-in users (customers and admins) are immediately logged out. |
| **Signed Routes** | HMAC-SHA256 signature verification | All temporary and signed links (email verification, password reset, cancel-email-change) fail validation immediately with a `403 Invalid Signature`. |

---

## 3. Production Procedure: Dual-Key Rotation

Laravel 11/12 includes native support for **previous keys**, allowing the application to safely read data encrypted with old keys while writing all new data with the rotated key.

### Step 1: Record Current Key
Retrieve the current `APP_KEY` from the production environment:
```bash
grep APP_KEY .env
# Example output: APP_KEY=base64:tvKpXd0Ba7M9R3i0WQqLTw9Z5P1so3UP22G1Wpwoh/U=
```

### Step 2: Append to Previous Keys
Copy the exact base64 value and add it to `APP_PREVIOUS_KEYS` in your production environment variables. If you already have existing keys there, separate them with a comma:
```env
APP_PREVIOUS_KEYS=base64:tvKpXd0Ba7M9R3i0WQqLTw9Z5P1so3UP22G1Wpwoh/U=
```
> [!NOTE]
> Setting `APP_PREVIOUS_KEYS` ensures Laravel can still successfully decrypt database records or verify signatures generated by this old key.

### Step 3: Generate the New APP_KEY
Run the Artisan command to overwrite the `APP_KEY` with a fresh 32-byte secret:
```bash
php artisan key:generate
```
Laravel will update `APP_KEY` in `.env` to the new secret (e.g., `APP_KEY=base64:7MY/b6Tyc2gKYyqzR/ebgVFedqhPxVH41XHEk+HR0Tk=`).
*At this point, all new cookies, signed URLs, and database records will be encrypted with the new key, while older ones can still be decrypted using the key listed in `APP_PREVIOUS_KEYS`.*

### Step 4: Re-Encrypt Database Records
To migrate legacy encrypted columns to the new key, run a re-encryption task. You can write a temporary command or script to load, decrypt, and save the models:

```php
// Example database re-encryption script
use App\Models\User;

User::chunk(100, function ($users) {
    foreach ($users as $user) {
        // Accessing the attribute decrypts it (using previous keys fallback if needed)
        // Re-saving encrypts the value using the new active APP_KEY
        if ($user->sensitive_column) {
            $user->sensitive_column = $user->sensitive_column;
            $user->save();
        }
    }
});
```

### Step 5: Clean Up Previous Keys
Once all database records have been re-saved/re-encrypted under the new active key, you can safely remove the old key from `APP_PREVIOUS_KEYS` in the production environment variables:
```env
APP_PREVIOUS_KEYS=
```
This finalizes the key rotation process, leaving the system fully secured under the new rotated key.
